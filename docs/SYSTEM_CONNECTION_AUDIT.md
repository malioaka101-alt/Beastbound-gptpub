# Beastbound — connecting the existing systems before adding more (13 November 2026)

**Authority:** Original `Beastbound_Realms_Unified_Master_Prompt.md` §§19, 35–36, 39, 41–50, 54, 57; `docs/MASTER_PROMPT_DEPTH_CHECKLIST.md`; `reference/Beastbound_Table_Rules.md`. This is a **review of code that currently exists on `main`**, not a new mechanical subsystem, permission framework, universal progression formula or exhaustive fantasy content list. Neither apparent conceptual similarity nor the same object mentioned by two systems implies permission to merge their separate rules or grant an effect.

## Consolidation audit: shared proofs, independent rules (13 November 2026)

**Duplicate monetary verification:** `world/person-careers.js` and `world/independent-local-purchases.js` each checked the same before/after Scales conservation independently. Their actual existing receipts now reuse the **pure** `rules/core.js` conserved-Scales check. Actual person choice, payee identity, work completion, seller stock, demand, money movements, and persistence remain in their original owners. No additional ledger, payment, RNG or buyer is created.

**Duplicate ownership adapter:** built instruments and paid equipment already publish their own verified `ownedAsset` source. `rules/material-handoffs.js` now consumes their shared `kind/owner/quantity/originalRoot/source` result instead of reconstructing separate provenance labels. Only the owning system determines whether the item exists. A quote, proposal or document never creates goods, magic, legal title or consent.

**Not merged:** employment agreements are not paid labour; posted demand is not funded purchases; beast consent and human powers are not universal ranks; local legal rights, supply sources and ecological change retain their respective original systems. #19 remains open for true actor/good generality; the goal is a connected foundation rather than additional individually scripted examples.

## Integrate first where overlap already exists

**1. Reuse verified shared work proof (#19 / #24).** PR #95 completed the exact-head three-batch regression and final gate and **merged** at `e14a448cae39978bacaff052ebbd399704a58862`. Its existing work, repair and material receipts should be one source of evidence for real downstream property consequences; no further item-specific PR is implied. One more distinct *source-established* activity will later test generality, not a pre-created library of fantasy recipes.

**2. Audit and connect real transaction/custody witnesses (#19).** Inspect `rules/equipment.js`, `rules/material-handoffs.js`, `world/person-careers.js`, `world/merchant-voluntary-work-terms.js` and `world/independent-local-purchases.js` as one interaction chain. The missing reusable boundary is still a genuine alternative **sourced actor/good and correct same-unit conserved transfer**, not another hardcoded ration merchant. Reuse original owner and worker records; do not build a second finance or permissions system.

**3. Connect world consequences, not world engines (#18 / #20 / #22 / #25).** Work, rescue, environmental damage, nonhuman consent, organisation and legal effects must each reach the **same real person/location/date/world history**. Keep distinct NPC decisions, clinical realities and local law. Repair an observed broken handoff rather than manufacture a general synthetic 'world consequence' pathway.

**4. Keep cross-discipline interfaces narrow (#16 / #23 / #24).** Existing coherence, partnership, combat, equipment and body/Origin mechanics can observe one another's *verified capabilities* but must never substitute one cultivation structure for another or infer compatibility from a label.

## How a merger or adapter earns its place

1. Name a **real cross-system event** and identify the state owner already responsible for it. If no live event fails, prefer no code change.
2. Prefer calling or extracting a pure shared validator from the **existing authoritative module**. Keep event-specific checks and independent character choices in their own owners.
3. Verify old save compatibility, exact original RNG/roll count, resource conservation, world tick timing, source hashes, player knowledge/privacy, NPC/beast consent and replay.
4. Write a **common-invariant regression** in the existing test group (plus one unlike source-backed example if needed); do not add a subsystem and tests for every object.
5. Reassess checklist acceptance immediately after essential shared connections pass. **No more optional feature PR chains as blockers.**
